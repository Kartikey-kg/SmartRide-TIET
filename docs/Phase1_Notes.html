Project Overview & Tech Stack

SmartRideTIET is a campus ride-sharing web application built exclusively for students and staff at Thapar Institute of Engineering & Technology (TIET). It allows students to book rides, drivers to accept them, and admins to monitor everything — all in real time.

🏗️ What We Are Building

User TypeWhat They Can Do
🎓 StudentRegister, book rides, track driver live, pay online, view history
🚕 DriverRegister, see available ride requests, accept/complete rides, track earnings
👑 AdminView all users, all rides, revenue stats, manage roles

🛠️ Final Tech Stack (Why We Chose Each)

LayerTechnologyWhy This?
Frontend (UI)React.js + ViteFast, component-based, runs in browser, easy in VS Code
Backend (API)Node.js + ExpressJavaScript everywhere, fast, handles many users
DatabaseFirebase FirestoreNo SQL needed, real-time sync, free tier, cloud-hosted
AuthenticationFirebase AuthBuilt-in login system, handles Google sign-in, secure
MapsGoogle Maps APIIndustry standard, shows routes and live tracking
PaymentsRazorpayIndian payment gateway, supports UPI/QR/card
HostingFirebase HostingFree, fast, connected to our Firebase project
💡
Why not Flutter + MongoDB?
We replaced Flutter (mobile app) with React PWA (works on phone browser — no app install needed) and MongoDB with Firebase Firestore (no database server to manage, everything is cloud-based).

Key Concepts Explained

🔷 Frontend

The part of the app the user sees and interacts with — the buttons, forms, pages. Built with React.js. It runs inside the user's browser.

🔷 Backend

The hidden server that processes logic, checks rules, and talks to the database. Built with Node.js + Express. Runs on a server (port 5000).

🔷 API (Application Programming Interface)

A set of URLs the frontend calls to get or send data. Example: POST /api/rides/book = "book a ride". The backend listens for these calls and responds.

🔷 REST API

A way to organize API endpoints using HTTP methods: GET (read data), POST (create data), PUT (update data), DELETE (remove data).

🔷 Firebase

Google's app development platform. We use 3 Firebase services: (1) Auth = login system, (2) Firestore = database, (3) Hosting = deploy frontend.

🔷 Firestore

A cloud NoSQL database. Data is stored in "collections" (like folders) and "documents" (like files). Example: users/userId123 = one user's data.

🔷 Firebase Auth

Firebase's built-in authentication system. Handles email+password login, Google sign-in, token generation, and session management without us writing any auth code from scratch.

🔷 JWT (JSON Web Token)

A secure token given to a user after login. The frontend sends this token with every API request. The backend verifies it to confirm who is making the request.

🔷 Middleware

Code that runs between receiving a request and sending a response. Example: our auth middleware checks "Is this user logged in?" before letting them access protected routes.

🔷 Environment Variables (.env)

Secret keys and config values stored in a .env file, NOT in the code. This keeps API keys private and out of GitHub. Frontend uses VITE_ prefix, backend uses no prefix.

🔷 React Context

A way to share data (like "who is logged in?") across all React components without passing it through every component manually. Our AuthContext provides user info to the whole app.

🔷 Axios

A JavaScript library that makes HTTP requests from the frontend to the backend easy. Like a messenger that sends/receives data between frontend and backend.

🔷 Vite

A super-fast build tool for React apps. It's the modern replacement for Create React App. Starts the dev server almost instantly. Uses npm run dev.

🔷 Nodemon

A tool that automatically restarts the Node.js server whenever you save a file. Without it, you'd have to manually stop and restart the server after every code change.

🔷 CORS (Cross-Origin Resource Sharing)

A browser security rule that blocks requests between different addresses. Our React app (port 5173) talking to our backend (port 5000) would be blocked without CORS. We configure it to allow this.

Backend Files — Code Explained

📄 backend/server.js — The Main Entry Point

What: This is the first file Node.js runs. It creates the Express app, connects all routes, and starts listening for requests on port 5000.

Why: Every backend needs a starting point. This is it.

How it works: Think of it as the "reception desk" — it receives all incoming requests and directs them to the right department (route).

const express = require('express');    // Web framework
const cors    = require('cors');       // Allow frontend to talk to backend
const dotenv  = require('dotenv');    // Load .env file
dotenv.config();                         // Reads .env into process.env

require('./config/firebase');           // Initialize Firebase first

// Import all route files
const authRoutes  = require('./routes/auth.routes');
const rideRoutes  = require('./routes/ride.routes');

const app = express();
const PORT = process.env.PORT || 5000;   // Use .env PORT or 5000

// CORS: Allow requests from React app (port 5173)
app.use(cors({ origin: 'http://localhost:5173' }));
app.use(express.json());                // Parse JSON request bodies

// Mount routes at specific URL prefixes
app.use('/api/auth',  authRoutes);
app.use('/api/rides', rideRoutes);

app.listen(PORT, () => {
  console.log(`✅ Server running on port ${PORT}`);
});server.js

📄 backend/config/firebase.js — Firebase Admin SDK

What: Connects the backend to Firebase using a secret service account key. Gives the backend admin-level access to Firestore and Auth.

Why: The frontend uses Firebase with limited permissions. The backend needs admin access to verify tokens, read/write any user's data, and delete accounts.

How it works: Like giving the backend a master key to the Firebase database.

⚠️
Firebase Admin vs Firebase Client — Key Difference
Client SDK (frontend): limited access, needs user login, runs in browser.
Admin SDK (backend): full access, no login needed, runs on server only. NEVER use Admin SDK in frontend! 
// New modular API (firebase-admin v11+)
const { initializeApp, getApps, cert } = require('firebase-admin/app');
const { getFirestore } = require('firebase-admin/firestore');
const { getAuth }      = require('firebase-admin/auth');

// getApps().length === 0 prevents initializing twice
if (getApps().length === 0) {
  let credential;
  try {
    const serviceAccount = require('./serviceAccountKey.json');
    credential = cert(serviceAccount);   // Use JSON file if available
  } catch {
    credential = cert({                  // Else use .env variables
      projectId:   process.env.FIREBASE_PROJECT_ID,
      clientEmail: process.env.FIREBASE_CLIENT_EMAIL,
      privateKey:  process.env.FIREBASE_PRIVATE_KEY?.replace(/\\n/g, '\n'),
    });
  }
  initializeApp({ credential });
}

const db   = getFirestore();   // Database instance
const auth = getAuth();        // Auth instance
module.exports = { db, auth };config/firebase.js

📄 backend/middleware/auth.middleware.js — Security Guard

What: Two functions that protect API routes: verifyToken (checks if user is logged in) and requireRole (checks if user has the right role).

Why: Without this, anyone could call /api/admin/stats without being an admin. This middleware blocks unauthorized access.

How it works: Like a bouncer at a club — first checks your ID (token), then checks your membership level (role).

// verifyToken — checks the Bearer token in the request header
const verifyToken = async (req, res, next) => {
  const token = req.headers.authorization?.split(' ')[1]; // "Bearer TOKEN"
  if (!token) return res.status(401).json({ error: 'No token' });

  const decoded = await auth.verifyIdToken(token); // Firebase checks token
  req.user = decoded;  // Attach user info to request
  next();              // Continue to route handler
};

// requireRole — checks Firestore for user's role
const requireRole = (...roles) => async (req, res, next) => {
  const doc  = await db.collection('users').doc(req.user.uid).get();
  const role = doc.data().role;          // 'student' | 'driver' | 'admin'
  if (!roles.includes(role)) return res.status(403).json({ error: 'Forbidden' });
  next();
};auth.middleware.js

const router = require('express').Router();

// POST /api/rides/book → Student books a ride
router.post('/book', verifyToken, requireRole('student'), rideController.bookRide);
//              ↑            ↑                    ↑                    ↑
//           URL path    Must be logged in   Must be student     Actual function

// PUT /api/rides/:id/accept → Driver accepts a ride
router.put('/:id/accept', verifyToken, requireRole('driver'), rideController.acceptRide);ride.routes.js

📄 backend/controllers/ — Business Logic

What: The actual functions that run when a route is hit. They read/write Firestore data and send back a response.

Why separate from routes? Keeps code clean. Routes = "what URL", Controllers = "what to do".

// auth.controller.js — registerUser function
const registerUser = async (req, res) => {
  const { name, phone, role } = req.body;  // Get data from request
  const uid   = req.user.uid;              // From Firebase token
  const email = req.user.email;

  // Create a document in Firestore: users/uid
  await db.collection('users').doc(uid).set({
    uid, name, email, phone, role,
    totalRides: 0,
    createdAt: new Date().toISOString()
  });

  res.status(201).json({ message: 'User registered!' });
};auth.controller.js

📄 frontend/src/services/api.js — API Client

What: A pre-configured Axios instance. All backend API calls go through this file.

Why: Instead of writing full URLs and auth headers in every component, we configure it once here. The interceptor automatically attaches the Firebase token to every request.

import axios from 'axios';
import { auth } from './firebase';

const api = axios.create({
  baseURL: 'http://localhost:5000/api',   // Backend URL
});

// Interceptor: runs BEFORE every request
// Automatically gets Firebase token and adds it to header
api.interceptors.request.use(async (config) => {
  const user  = auth.currentUser;
  if (user) {
    const token = await user.getIdToken();   // Get fresh JWT token
    config.headers.Authorization = `Bearer ${token}`;
  }
  return config;
});

// Pre-made API functions (used in components)
export const bookRide   = (data) => api.post('/rides/book', data);
export const getMyRides = ()     => api.get('/rides/my');services/api.js

📄 frontend/src/context/AuthContext.jsx — Global Auth State

What: A React Context that stores the current user's login status and profile. Available to every component in the app.

Why: Without context, you'd have to pass user as a prop through every component — very messy. Context makes it global.

How: Uses Firebase's onAuthStateChanged which fires automatically whenever user logs in or out.

const AuthContext = createContext(null);

export const AuthProvider = ({ children }) => {
  const [user, setUser]       = useState(null);   // Firebase user object
  const [profile, setProfile] = useState(null);   // Firestore user data

  useEffect(() => {
    // This listener fires whenever auth state changes (login/logout)
    const unsubscribe = onAuthStateChanged(auth, async (firebaseUser) => {
      if (firebaseUser) {
        setUser(firebaseUser);
        const res = await getMe();   // Fetch profile from backend
        setProfile(res.user);
      } else {
        setUser(null); setProfile(null);
      }
    });
    return () => unsubscribe();   // Cleanup listener
  }, []);

  // Values available to all components via useAuth() hook
  return (
    <AuthContext.Provider value={{ user, profile, isAdmin: profile?.role === 'admin' }}>
      {children}
    </AuthContext.Provider>
  );
};AuthContext.jsx

📄 frontend/src/App.jsx — All Routes

What: Defines all URL routes for the frontend. Which URL shows which page.

Why: React is a Single Page App (SPA) — it doesn't reload the page. React Router handles navigation between "pages" without real page loads.

function App() {
  return (
    <AuthProvider>                         // Wrap everything in auth context
      <Router>
        <Routes>
          // Public — anyone can access
          <Route path="/"      element={<LandingPage />} />
          <Route path="/login" element={<LoginPage />} />

          // Protected — only students
          <Route path="/student/dashboard" element={
            <ProtectedRoute allowedRoles={['student']}>
              <StudentDashboard />
            </ProtectedRoute>
          } />
        </Routes>
      </Router>
    </AuthProvider>
  );
}App.jsx

📄 frontend/src/components/common/ProtectedRoute.jsx

What: A wrapper component that checks if a user is logged in and has the right role before showing a page.

Why: Without this, any user could navigate to /admin/dashboard just by typing the URL.

const ProtectedRoute = ({ children, allowedRoles }) => {
  const { user, profile } = useAuth();

  if (!user)    return <Navigate to="/login" />;   // Not logged in → go to login
  if (!profile) return <Navigate to="/register" />; // No profile → register first

  // Wrong role → redirect to their own dashboard
  if (allowedRoles && !allowedRoles.includes(profile.role)) {
    if (profile.role === 'driver') return <Navigate to="/driver/dashboard" />;
    if (profile.role === 'admin')  return <Navigate to="/admin/dashboard" />;
  }

  return children;  // All checks passed — show the page
};ProtectedRoute.jsx

Errors Faced & How We Fixed Them

❌ Error 1 — PowerShell && not recognized
The token '&&' is not a valid statement separator in this version.

Why it happened: PowerShell uses semicolons ; or -and to chain commands, NOT && like Linux/Mac bash.

✅ Fix:

Use PowerShell's New-Item command to create multiple folders at once:

New-Item -ItemType Directory -Path "folder1", "folder2", "folder3" -Force
❌ Error 2 — Firebase Admin TypeError: Cannot read properties of undefined (reading 'length')
TypeError: Cannot read properties of undefined (reading 'length') at Object.<anonymous> (backend\config\firebase.js:15:17) if (!admin.apps.length) {

Why it happened: The old code used const admin = require('firebase-admin') and then admin.apps. In firebase-admin v11+, the package structure changed. The default export no longer has .apps directly.

✅ Fix — Use new modular imports:
// OLD (broken) const admin = require('firebase-admin'); if (!admin.apps.length) { admin.initializeApp({...}); } // NEW (correct for v11+) const { initializeApp, getApps, cert } = require('firebase-admin/app'); const { getFirestore } = require('firebase-admin/firestore'); if (getApps().length === 0) { initializeApp({ credential: cert(serviceAccount) }); }
❌ Error 3 — .env values not loading / undefined
FIREBASE_PROJECT_ID is undefined Firebase: Error - No Firebase App '[DEFAULT]' has been created

Why it happened: Either the .env file had quotes around values (breaking some parsers), or dotenv.config() was not called before using the values.

✅ Fix:
# WRONG — do not wrap normal values in quotes FIREBASE_PROJECT_ID="smartridetiet" # CORRECT — no quotes for normal values FIREBASE_PROJECT_ID=smartridetiet # Exception: private key NEEDS quotes (has \n newlines inside) FIREBASE_PRIVATE_KEY="-----BEGIN PRIVATE KEY-----\nABC...\n-----END PRIVATE KEY-----\n"
❌ Error 4 — Google Maps "Select one or more APIs" red error
Select one or more APIs (shown in red on API restriction popup)

Why it happened: After creating an API key, Google shows a restriction popup. The "Select Maps APIs" dropdown was required but left empty.

✅ Fix:

Click the "Select Maps APIs" dropdown → check: ☑ Maps JavaScript API, ☑ Directions API, ☑ Distance Matrix API → Click "Restrict key"

❌ Error 5 — Google Analytics confusion during Firebase project creation
Long page appeared with terms about data sharing, benchmarking, technical support...

Why it happened: Google Analytics was toggled ON by default during project creation. This shows a full terms page.

✅ Fix:

During Firebase project creation, on the second step — find the toggle "Enable Google Analytics for this project" and turn it OFF. The page disappears and you get a simple "Create project" button.

❌ Error 6 — Firestore "Create database" popup was different from instructions
Step 1: Select edition (Standard / Enterprise) Step 2: Database ID & location Step 3: Configure — was shown instead of just "Start in test mode" popup

Why it happened: Firebase updated their UI. The old single-popup is now a 3-step wizard.

✅ Fix:

Step 1: Keep "Standard edition" selected → Next. Step 2: Change location to asia-south1 → Next. Step 3: Select "Start in test mode" → Create.
