Key Concepts Explained

🔷 Firebase Authentication

Google's ready-made login system. Instead of writing code to hash passwords, manage sessions, and handle token expiry yourself, Firebase does it all. You just call signInWithEmailAndPassword() and Firebase handles everything.

🔷 JWT (JSON Web Token)

A secure, signed string that proves your identity. After login, Firebase gives you a JWT (called an "ID Token"). Every API call sends this token in the header. The backend uses Firebase Admin SDK to verify the token is real and not tampered with.

🔷 React Context API

A built-in React feature for sharing data globally. Without Context, you'd have to pass user as a prop through every component. With Context, any component anywhere in the app can call useAuth() and get user data instantly.

🔷 onAuthStateChanged

A Firebase listener that fires every time the user's auth status changes — on login, logout, or page refresh. This is how the app "remembers" you're logged in even after refreshing the page. It reads your session from localStorage automatically.

🔷 Protected Route

A React wrapper component that checks if the user is logged in before showing a page. If not logged in → redirect to /login. If wrong role → redirect to their own dashboard. If all checks pass → show the page. It's the security gatekeeper of the frontend.

🔷 Axios Interceptor

A function that runs automatically before every HTTP request or after every response. The request interceptor gets the Firebase JWT token and attaches it to every API call — so you never have to manually add the token. The response interceptor catches 401 errors and logs the user out.

🔷 Firebase Admin SDK (Backend)

The server-side Firebase library. The client SDK (frontend) has limited permissions. The Admin SDK (backend) has full admin access — it can verify any user's token, read any document, delete any account. It uses a service account key (a JSON file with private key) for authentication.

🔷 Role-Based Access Control (RBAC)

A system where what you can do depends on your role. In SmartRideTIET: students can book rides, drivers can accept rides, admins can see everything. The role is stored in Firestore and checked on both frontend (ProtectedRoute) and backend (requireRole middleware).

🔷 Google OAuth (Sign In with Google)

An industry-standard login method. Instead of entering email + password, you click "Sign in with Google" and a popup opens. Google verifies you're really you and sends a token to the app. Firebase wraps this process with signInWithPopup(auth, googleProvider).

🔷 Optional Chaining (?.) in JavaScript

A safe way to access nested properties. profile?.role returns undefined if profile is null, instead of crashing with "Cannot read property 'role' of null". Used everywhere in Phase 2 because profile data loads asynchronously.

🔷 NavLink (React Router)

Like <Link> but smarter — it automatically adds an active class to the link when the current URL matches. Used in the Navbar to visually highlight which page you're on.

🔷 useRef (React Hook)

Creates a reference to a DOM element. In the Navbar dropdown, we use useRef to detect when you click outside the dropdown menu, so it closes automatically. dropdownRef.current.contains(e.target) checks if the click was inside the dropdown.

Frontend Files — Code Explained

📄 frontend/vite.config.js — Build Tool Config

What: Tells Vite how to build the project. Adds the React plugin so Vite can handle JSX syntax and Fast Refresh (live reload without losing state).

Why: Without this file, Vite doesn't know React exists. JSX (the HTML-like syntax in .jsx files) would cause build errors because browsers don't understand JSX natively.

How it works: The react() plugin uses Babel under the hood to transform JSX into plain JavaScript that browsers can run.

import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],   // ← This is what enables JSX in your .jsx files
  server: {
    port: 5173,          // dev server port
    open: true,          // auto-opens browser tab on npm run dev
  },
  resolve: {
    alias: { '@': '/src' }, // lets you write @/context/AuthContext instead of ../../context/AuthContext
  },
});vite.config.js

📄 frontend/src/services/firebase.js — Firebase Client SDK

What: Initializes Firebase for the browser. Exports three things: auth (for login/logout), db (for Firestore database), and googleProvider (for Google OAuth popup).

Why: You need one single initialized Firebase app shared across all files. If each file calls initializeApp() separately, Firebase throws a "duplicate app" error.

How it works: Reads all keys from the .env file using import.meta.env.VITE_*. Vite only exposes variables that start with VITE_ for security.

  authDomain:        import.meta.env.VITE_FIREBASE_AUTH_DOMAIN,
  projectId:         import.meta.env.VITE_FIREBASE_PROJECT_ID,
  storageBucket:     import.meta.env.VITE_FIREBASE_STORAGE_BUCKET,
  messagingSenderId: import.meta.env.VITE_FIREBASE_MESSAGING_SENDER_ID,
  appId:             import.meta.env.VITE_FIREBASE_APP_ID,
};

const app = initializeApp(firebaseConfig);  // Initialize once

📄 frontend/src/context/AuthContext.jsx — The Brain of Auth

What: The most important file in Phase 2. Creates a global "broadcast channel" for auth state. Holds the logged-in user data and provides login/logout functions to the whole app.

Why: Every page needs to know "who is logged in". Without Context, you'd pass user as props through 10+ layers of components. With AuthContext, any component anywhere calls const {profile} = useAuth() and gets the data.

How it works: Listens to onAuthStateChanged which fires when the user logs in, logs out, or the page refreshes. On login, fetches the extended profile from our backend (Firestore data).

// Step 1: Create a Context (like creating a radio channel)
const AuthContext = createContext(null);

// Step 2: Custom hook — any component uses this to "tune in"
export const useAuth = () => useContext(AuthContext);

// Step 3: Provider component — wraps the entire app in App.jsx
export const AuthProvider = ({ children }) => {
  const [user, setUser]       = useState(null);  // Firebase auth user object
  const [profile, setProfile] = useState(null);  // Firestore user document
  const [loading, setLoading] = useState(true);  // true while Firebase resolves auth

  // Step 4: Listen for auth state changes (fires on every login/logout/refresh)
  useEffect(() => {
    const unsubscribe = onAuthStateChanged(auth, async (firebaseUser) => {
      if (firebaseUser) {
        setUser(firebaseUser);
        const res = await getMe();   // GET /api/auth/me → fetch Firestore profile
        setProfile(res.user);
      } else {
        setUser(null); setProfile(null);
      }
      setLoading(false);  // auth is now resolved — app can render
    });
    return () => unsubscribe();  // cleanup when app unmounts
  }, []);

  // Step 5: Auth functions used in LoginPage and RegisterPage
  const signInWithEmail = async (email, password) => {
    const { user: fbUser } = await signInWithEmailAndPassword(auth, email, password);
    const res = await getMe();       // fetch existing Firestore profile
    setProfile(res.user);
    return { user: fbUser, profile: res.user };  // ← returned so LoginPage can redirect by role
  };

  // Step 6: Provide all auth data and functions to all child components
  return (
    <AuthContext.Provider value={{ user, profile, loading, signInWithEmail, logout, ... }}>
      {!loading && children}  // Don't render anything until Firebase resolves auth state
    </AuthContext.Provider>
  );
};AuthContext.jsx
💡
Why {!loading && children}?
When the page first loads, Firebase takes ~0.5 seconds to check if a user is already logged in from a previous session. During that time, loading = true. If we rendered children during loading, ProtectedRoute would see user = null (not yet loaded) and wrongly redirect a logged-in user to /login.

📄 frontend/src/services/api.js — Axios API Client

What: A configured Axios instance that automatically attaches the Firebase JWT token to every API request, and handles 401 errors globally.

Why: Every API call needs the auth token. Instead of writing token-fetching code in every component, we write it once in an interceptor and it runs automatically for all requests.

import axios from 'axios';
import { auth } from './firebase';

const api = axios.create({
  baseURL: import.meta.env.VITE_API_BASE_URL || 'http://localhost:5000/api',
  headers: { 'Content-Type': 'application/json' },
});

// REQUEST INTERCEPTOR — runs before EVERY API call
api.interceptors.request.use(async (config) => {
  const user = auth.currentUser;
  if (user) {
    const token = await user.getIdToken();          // get fresh JWT from Firebase
    config.headers.Authorization = `Bearer ${token}`; // attach to request header
  }
  return config;
});

// RESPONSE INTERCEPTOR — runs after EVERY API response
api.interceptors.response.use(
  (response) => response.data,  // unwrap so you get {user} not {data:{user}}
  (error) => {
    if (error.response?.status === 401) {
      auth.signOut();                    // token expired → force logout
      window.location.href = '/login';
    }
    return Promise.reject(error.response?.data || error);
  }
);

// Named exports — one function per API endpoint
export const registerUser     = (data) => api.post('/auth/register', data);
export const getMe            = ()     => api.get('/auth/me');
export const updateMe         = (data) => api.put('/auth/me', data);
export const bookRide         = (data) => api.post('/rides/book', data);
export const getAvailableRides = ()    => api.get('/rides/driver/available');
export const acceptRide       = (id)   => api.put(`/rides/${id}/accept`);api.js

    'auth/wrong-password':     'Incorrect password.',

    'auth/too-many-requests':  'Too many attempts. Try again later.',
    'auth/invalid-credential': 'Invalid email or password.',
    'auth/popup-closed-by-user': '',  // user closed Google popup — not an error
  };
  return map[code] || 'Something went wrong. Please try again.';

📄 frontend/src/components/common/ProtectedRoute.jsx — Route Guard

What: A wrapper component placed around every protected page in App.jsx. Checks three conditions before allowing access.

Why: Anyone could type /admin/dashboard in the URL bar. Without ProtectedRoute, they'd see it. This component prevents that.

const ProtectedRoute = ({ children, allowedRoles = [] }) => {
  const { user, profile, loading } = useAuth();
  const location = useLocation();

  // Case 1: Auth state still loading → show spinner (never redirect prematurely)
  if (loading) return <LoadingSpinner />;

  // Case 2: Not logged in → go to login (save current URL for return redirect)
  if (!user) return <Navigate to="/login" state={{ from: location }} replace />;

  // Case 3: Logged in but wrong role → redirect to own dashboard
  if (allowedRoles.length > 0 && !allowedRoles.includes(profile?.role)) {
    const redirects = {
      student: '/student/dashboard',
      driver:  '/driver/dashboard',
      admin:   '/admin/dashboard',
    };
    return <Navigate to={redirects[profile?.role] || '/'} replace />;
  }

  // Case 4: All checks pass → show the page!
  return children;
};ProtectedRoute.jsx

📄 backend/config/firebase.js — Firebase Admin SDK

What: Initializes Firebase on the server side using Admin SDK. Exports db and auth for use in controllers and middleware.

Why: The frontend Firebase SDK has limited permissions (only reads what the logged-in user can read). The Admin SDK has full access — it can verify any user's token, read any document, and delete any account. It uses a service account key (secret JSON file).

const { initializeApp, getApps, cert } = require('firebase-admin/app');
const { getFirestore } = require('firebase-admin/firestore');
const { getAuth }      = require('firebase-admin/auth');

// getApps().length prevents initializing twice if this file is imported multiple times
if (getApps().length === 0) {
  let credential;
  try {
    const sa = require('./serviceAccountKey.json');  // use JSON file if available
    credential = cert(sa);
  } catch {
    credential = cert({                   // fallback: use .env variables
      projectId:   process.env.FIREBASE_PROJECT_ID,
      clientEmail: process.env.FIREBASE_CLIENT_EMAIL,
      privateKey:  process.env.FIREBASE_PRIVATE_KEY?.replace(/\\n/g, '\n'),
      // ↑ .env stores \n as literal text, .replace() converts back to real newlines
    });
  }
  initializeApp({ credential });
}

const db   = getFirestore();
const auth = getAuth();
module.exports = { db, auth };config/firebase.js

📄 backend/middleware/auth.middleware.js — Security Guard

What: Two middleware functions: verifyToken checks if the JWT is valid, and requireRole checks if the user has the right role for that endpoint.

Why: The backend cannot trust anything the frontend says. Even if the frontend hides the "Admin" button from a student, a student could still call POST /api/admin/delete-user directly using Postman or curl. The middleware blocks this on the server.

// Middleware 1: verifyToken
const verifyToken = async (req, res, next) => {
  const authHeader = req.headers.authorization;  // "Bearer eyJhb..."
  if (!authHeader?.startsWith('Bearer '))
    return res.status(401).json({ error: 'No token provided' });

  const token   = authHeader.split(' ')[1];             // extract just the token
  const decoded = await auth.verifyIdToken(token); // Firebase cryptographically verifies
  req.user = decoded;  // { uid, email, ... } — now available in all controllers
  next();              // proceed to next middleware or controller
};

// Middleware 2: requireRole (used like: requireRole('student') or requireRole('admin'))
const requireRole = (...roles) => async (req, res, next) => {
  const userDoc  = await db.collection('users').doc(req.user.uid).get();
  const userRole = userDoc.data().role;
  if (!roles.includes(userRole))
    return res.status(403).json({ error: `Forbidden. Needs: ${roles.join('/')}` });
  next();
};

// How they chain together in routes:
router.post('/book', verifyToken, requireRole('student'), rideController.bookRide);
//              ↑            ↑                    ↑                  ↑
//           URL       1. check JWT     2. check role=student   3. run logicauth.middleware.js

📄 backend/controllers/auth.controller.js — User Profile Logic

What: Four functions for user profile CRUD: create profile after signup, read profile, update profile, delete account.

Why: Firebase Auth only stores email + password. All other user data (name, phone, role, vehicle number) lives in Firestore. This controller manages that data.

// registerUser — POST /api/auth/register
// Called ONCE right after Firebase creates the auth account
const registerUser = async (req, res) => {
  const { name, phone, role, vehicleNumber, vehicleType } = req.body;
  const uid   = req.user.uid;    // from Firebase JWT (set by verifyToken)
  const email = req.user.email;

  // Check if already registered (prevents duplicate Firestore documents)
  const existing = await db.collection('users').doc(uid).get();
  if (existing.exists) return res.status(409).json({ error: 'Already registered' });

  const userData = {
    uid, name, email, phone, role,
    isActive: true, totalRides: 0, rating: 0,
    createdAt: new Date().toISOString(),
  };

  // Driver gets extra fields
  if (role === 'driver') {
    userData.vehicleNumber = vehicleNumber || '';
    userData.vehicleType   = vehicleType   || '';
    userData.isAvailable   = false;   // offline by default
    userData.earnings      = 0;
  }

  // Write to Firestore: users/{uid} document
  await db.collection('users').doc(uid).set(userData);
  res.status(201).json({ message: 'Registered!', user: userData });
};

// updateMe — PUT /api/auth/me
const updateMe = async (req, res) => {
  const { name, phone, vehicleNumber, vehicleType } = req.body;
  const updates = { updatedAt: new Date().toISOString() };
  // Only update fields that were actually sent
  if (name)          updates.name          = name;
  if (phone)         updates.phone         = phone;
  if (vehicleNumber) updates.vehicleNumber = vehicleNumber;
  if (vehicleType)   updates.vehicleType   = vehicleType;

  await db.collection('users').doc(req.user.uid).update(updates);
  res.json({ message: 'Profile updated!', updates });
};auth.controller.js

Auth Flow — How Everything Connects

🆕 New User Sign-Up Flow

User fills RegisterPage (name, email, role, password) ↓ signUpWithEmail() in AuthContext is called ↓ Firebase creates auth account (email + password stored securely by Google) ↓ POST /api/auth/register is called (with Firebase JWT token in header) ↓ Backend verifyToken middleware verifies the JWT ↓ auth.controller registerUser saves profile to Firestore users/{uid} ↓ profile.role read → redirect to /student/dashboard or /driver/dashboard

🔑 Returning User Sign-In Flow

User fills LoginPage (email + password) ↓ signInWithEmailAndPassword(auth, email, password) ↓ Firebase validates password → returns Firebase user + JWT token ↓ GET /api/auth/me called (with JWT in header) ↓ auth.controller getMe reads Firestore users/{uid} document ↓ profile data returned → redirectByRole(profile.role)

🛡️ ProtectedRoute Decision Tree

User navigates to /student/dashboard ↓ ProtectedRoute checks auth state │ ├─ loading = true? → Show loading spinner (wait for Firebase) │ ├─ user = null? → Navigate to /login (save current URL) │ ├─ wrong role? → Navigate to correct dashboard │ (driver → /driver/dashboard) │ └─ ✅ All checks pass → Render StudentDashboard

🔗 Every Authenticated API Call

Component calls bookRide(data) from api.js ↓ Axios request interceptor fires → user.getIdToken() gets fresh JWT ↓ Request sent with header: Authorization: Bearer eyJhb... ↓ Express backend receives request → verifyToken middleware runs ↓ auth.verifyIdToken(token) → Firebase Admin cryptographically validates token ↓ req.user = { uid, email } → requireRole middleware checks Firestore role ↓ Controller runs → reads/writes Firestore → sends JSON response

Errors Faced & How We Fixed Them

❌ Error 1 — Vite: Failed to resolve "@vitejs/plugin-react"
Failed to resolve import "@vitejs/plugin-react" from "vite.config.js"

Why it happened: vite.config.js imports @vitejs/plugin-react but it wasn't installed. The original project setup didn't install this package separately.

✅ Fix:
npm install @vitejs/plugin-react # Output: added 1 package ← confirms it installed
❌ Error 2 — PowerShell: "&&" not recognized
The token '&&' is not a valid statement separator in this version.

Why it happened: On Windows PowerShell, you cannot chain commands with && (that's Linux bash syntax). Tried to run mkdir pages/student && mkdir pages/driver.

✅ Fix — Use PowerShell syntax:
New-Item -ItemType Directory -Force -Path "pages/student", "pages/driver" # Or run commands on separate lines, or use ; between them
❌ Error 3 — White screen / App renders nothing
[No visible error in browser — just a blank white page]

Why it happened: Either a missing .env variable caused Firebase to fail silently, OR an import error in one of the pages crashed the app before anything rendered, OR loading in AuthContext never became false.

✅ Fix — Check browser Console (F12):

Open F12 → Console tab → the real error shows there. Common fixes:
• Verify frontend/.env has all VITE_FIREBASE_* values
• Run npx vite build to catch import errors
• Check all imported file names match exactly (case-sensitive)

❌ Error 4 — TypeError: Cannot read properties of null (reading 'role')
TypeError: Cannot read properties of null (reading 'role') at ProtectedRoute (ProtectedRoute.jsx:15)

Why it happened: Code used profile.role without checking if profile is null first. During the brief loading period, profile is null — accessing .role on null crashes.

✅ Fix — Always use optional chaining (?.):
// ❌ Crashes: profile.role // ✅ Safe: profile?.role // ✅ With default: profile?.name?.split(' ')[0] || 'User'
❌ Error 5 — CORS Error: No 'Access-Control-Allow-Origin' header
Access to XMLHttpRequest at 'http://localhost:5000/api/auth/me' from origin 'http://localhost:5173' has been blocked by CORS policy

Why it happened: Frontend (port 5173) calling backend (port 5000) — browser blocks this by default for security. The backend needs to explicitly allow this.

✅ Fix — in backend/server.js:
app.use(cors({ origin: 'http://localhost:5173', // ← must exactly match frontend URL credentials: true, }));
❌ Error 6 — 409 Conflict: User already registered
{"error": "User already registered."}

Why it happened: POST /api/auth/register was called twice for the same user. Can happen if Google sign-in is clicked twice, or if registerUser is called when it shouldn't be.

✅ Fix — The signInWithGoogle function handles this:

It tries getMe() first. If the user exists, it uses that profile. Only calls registerUser if getMe() returns a 404 (user doesn't exist yet in Firestore).

❌ Error 7 — Firebase popup-closed-by-user shown as error
Firebase: Error (auth/popup-closed-by-user)

Why it happened: User closed the Google sign-in popup without completing sign-in. Firebase throws an error for this, but it's just normal user behavior — not a real error.

✅ Fix — Catch this specific error code and show nothing (or a gentle message):
if (err.code === 'auth/popup-closed-by-user') { return; // just ignore it — user cancelled intentionally }
❌ Error 8 — useAuth must be used within AuthProvider
Error: useAuth must be used within AuthProvider

Why it happened: A component called useAuth() but it's not inside <AuthProvider> in the tree. Usually means AuthProvider is missing from App.jsx.

✅ Fix — Wrap everything in App.jsx:
function App() { return ( <AuthProvider> {/* ← MUST wrap Router */} <Router> <Routes>...</Routes> </Router> </AuthProvider> ); }
